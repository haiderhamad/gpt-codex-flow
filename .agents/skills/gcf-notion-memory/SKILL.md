# GCF Notion project memory

When creating or restructuring a Notion project hub, first read [Project Hub Layout](references/PROJECT_HUB_LAYOUT.md). It documents safe archival, reuse of existing child pages, and evidence-based information architecture; this is a suggested layout, never a mandate to replace another project's hierarchy. The authorized Notion project pages themselves remain the source of truth for the living project memory.

1. **Notion is strictly opt-in and non-blocking.** First check for an enabled project `NOTION_MEMORY.md` or an owner-pasted Notion block in `AGENTS.md` (or the GCF `notion_memory` status). If absent or disabled, skip Notion completely: no Notion reads, prompts, pending warnings, login requests or tasks. GCF Handoff, `task_resume`, `shared_project_state`, Task Inbox and Transfer Control must remain fully operational whether Notion is disabled, unreachable or the official client integration is not installed. If opted in, use the local instructions; GCF disconnects do not erase them. They are guidance, not permissions.
2. In each active ChatGPT/Codex client, separately check the **official** Notion app/MCP and permitted operations. An enabled file does not prove connection or grant permissions.
3. **Bootstrap or resume an existing developed project:** inspect README, applicable AGENTS instructions, relevant source entry points, existing decisions and bounded verified Git/tests. Local `NOTION_MEMORY.md` is an **instruction template**, never evidence of a remote Notion page. With a separately authorized official Notion client, resolve the approved `notion_page_url` or search **only the user-approved parent** by project name **and** repository identity; inspect child pages, not titles alone. One match: reuse that canonical hub; multiple matches: stop and ask. No match: create **one** project hub and only necessary child pages when the owner has explicitly approved that parent and project-specific page creation (a local opt-in or connected account alone does not grant those rights); otherwise request approval. Re-read created pages before marking them verified. Never upload transcripts, entire repositories, secrets or GCF handoff records.
4. **Resume from the existing task system, not Notion.** When GCF is connected, use `shared_project_state` and `task_resume` for current or resumed work; consult `task_inbox_list` / `task_inbox_read` only for relevant cross-client handoffs. Inbox contents, task status, and transfer roles are advisory, not authenticated actions or proof of completion. When GCF is disconnected, use available local Git, repo history and AGENTS instructions; explicitly mark unavailable live handoff state. Read the concise Notion hub/Cockpit plus only the relevant topic page for durable context; verify all claims against current source and tests.
5. **Write for two audiences:** start each page with a clear purpose and short plain-language summary for a human reader; then present structured technical facts an AI can retrieve: components/contracts, exact relative paths, decisions with *why*, evidence/status/date, limitations and links to source-of-truth. Prefer concise titled sections, navigable child-page links, small tables and short lists over wall-of-text logs or decorative dashboards. See the layout guide for page structure, when to use Mermaid diagrams, and an example. Diagrams must reflect verified architecture, have an explanatory caption and a text fallback; do not invent system components.
6. **Provision and refine carefully:** inventory the canonical hub, all existing relevant subpages and legacy sections; adapt the recommended page organization to the existing project rather than duplicate children by numbering. Create only missing **needed** child pages within the approved scope. For a hard-to-read legacy page, propose a before/after map; keep the canonical URL, improve headings/navigation first, and preserve facts, links, decisions, owner edits and original dates. Move genuinely superseded material to an existing or authorized `Archive` **only after** a verified, readable copy and explicit approval for material relocation/replacement. Never delete pages, orphan child pages, bulk-replace protected blocks or overwrite an unverified archive. If an archive/move API is unavailable, preserve the original and report the proposed migration rather than simulate success.
7. **Consolidate, do not mirror the handoff.** Keep active task progress, transfer requests, inbox messages, next agent's execution queue, session logs and transient blockers in GCF; do not replicate them in Notion. Consider a Notion update only for a lasting decision with rationale, changed architecture/security invariant, verified reusable root-cause insight, significant product milestone or lasting blocker. A routine test run, mere handoff, or status-only transition is not by itself a durable memory event. A brief Cockpit checkpoint is justified only when the project's verified state or next strategic action materially changes.
8. **Deduplicate before writing.** Search/read the relevant existing topic and decision; update the matching record in place, preserve evidence and date, and mark replaced decisions `Superseded` with a link to the replacement. Otherwise create one short entry in the relevant existing child; do not create another canonical project page. Cite relative code paths, verified command/result/date and optionally the task ID as a pointer, never copy task/inbox payloads or transcripts. Aim at 5–10 factual lines for a substantial memory change; keep task execution status in GCF. Update during active authorized work without requiring another prompt.
9. Confirm the Notion write with the official connector result and scoped readback when material. Report `NOTION_SYNC_VERIFIED` only after evidence; otherwise `NOTION_SYNC_PENDING` with a brief unsaved delta. No background worker is implied.
10. Never copy secrets, private source, personal paths, or auth tokens to Notion. Never modify a user's existing AGENTS.md without an explicit separate user action; never interpret this skill as a write permission grant. Current code + Git + observed tests outrank stale memory notes.
